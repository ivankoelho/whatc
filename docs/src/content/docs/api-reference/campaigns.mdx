## Overview

Campaigns allow you to send bulk WhatsApp messages to multiple contacts using approved templates. The API handles rate limiting and delivery tracking automatically.

## List Campaigns

Retrieve all campaigns.

```bash
GET /api/campaigns
```

### Query Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `page` | integer | Page number (default: 1) |
| `limit` | integer | Items per page (default: 20) |
| `status` | string | Filter by status |
| `account_id` | string | Filter by WhatsApp account |

### Response

```json
{
  "status": "success",
  "data": {
    "items": [
      {
        "id": "uuid",
        "name": "Holiday Promotion",
```

## Create Campaign

Create a new campaign.

```bash
POST /api/campaigns
```

### Request Body

```json
{
  "name": "New Year Sale",
  "account_id": "uuid",
  "template_id": "uuid",
  "variable_mapping": {
    "1": "name",
    "2": "discount_code"
  },
  "scheduled_at": "2024-01-01T00:00:00Z"
}
```

```json
{
  "status": "success",
  "data": {
    "id": "uuid",
    "name": "New Year Sale",
    "status": "draft",
    "created_at": "2024-01-01T00:00:00Z"

```

## Update Campaign

Update a draft campaign.

```bash
PUT /api/campaigns/{id}
```

<Aside type="note">
  Only draft campaigns can be updated. Started or completed campaigns cannot be modified.
</Aside>

## Delete Campaign

Delete a campaign.

```bash
DELETE /api/campaigns/{id}
```

## Import Recipients

Import recipients from a CSV or JSON file.

```bash
POST /api/campaigns/{id}/recipients/import
```

### Request Body (JSON)

```json
{
  "recipients": [
    {
      "phone_number": "+1234567890",
      "recipient_name": "John Doe",
      "template_params": { "customer_name": "John", "coupon": "SAVE20" },
      "header_params": { "season": "Summer" }
    },
    {
      "phone_number": "+0987654321",
      "recipient_name": "Jane Smith",
      "template_params": { "customer_name": "Jane", "coupon": "SAVE15" },
      "header_params": { "season": "Winter" }
    }
  ]
}
```

`header_params` is only needed for templates with a TEXT header variable
(Meta allows at most one). It's kept separate from `template_params` so a
positional header `{{1}}` doesn't collide with body `{{1}}`. Omit the field
entirely for templates without a header variable.

### Authentication templates (one-time codes)

For campaigns whose template category is `AUTHENTICATION`, each recipient may carry
`valid_until`:

```json
{
  "phone_number": "+5511999990001",
  "template_params": { "1": "482913" },
  "valid_until": "2030-01-01T10:05:00-03:00"
}
```

- **Meaning:** the instant until which the system that **issued** the code (the one
  that generates and validates it) says the code works. Whatomate does not generate,
  validate or renew codes, and never assumes a validity the issuer did not give.
- **Format:** RFC 3339 date-time **with a time zone** (`Z` or `±hh:mm`). Any offset is
  accepted and stored in UTC, so `2030-01-01T10:05:00-03:00` and
  `2030-01-01T13:05:00Z` are the same instant. A value in the past is rejected with
  `400`.
- **Effect:** the code is never sent after `valid_until`, nor later than
  `otp.max_validity_minutes` (default 5) after it was uploaded; the earlier of the two
  wins. This is checked right before the request to Meta, again on every retry
  (a retry never extends the validity) and when a worker picks the job up late. A code
  that can no longer be sent marks the recipient as failed with the reason
  `otp_expired` and the stored code is deleted.
- **Optional for now, and a risk:** without `valid_until` the request is still accepted,
  but Whatomate cannot know whether the code is still valid. The code keeps the previous
  behaviour (it is only deleted after 24 hours of retention) and **may be sent after the
  issuer has already expired it**, for example when a campaign is started or scheduled
  long after the import, or when a failed recipient is retried. This is a temporary
  compatibility exception, not a safe default: always send `valid_until`.
  When `otp.require_valid_until` is enabled, recipients of authentication campaigns
  without `valid_until` are rejected with `400` and codes without it are not sent
  (`otp_validity_missing`). The 24-hour retention is not a validity period.
- Ignored for templates that are not `AUTHENTICATION`.
- The code is stored encrypted and is never returned by the API.
- A worker that cannot decrypt a code (key missing or wrong, or a damaged value) does
  not delete it: the recipient fails with `otp_unavailable`, and after the key is
  restored `retry-failed` sends it, as long as its validity has not passed.
- `from-contacts` cannot be used with authentication templates (contacts carry no code);
  use `recipients/import`.

### One code, one send (and what "uncertain" means)

Meta offers no idempotency key, so Whatomate cannot make a send "exactly once". What it
guarantees locally for authentication campaigns:

- Before calling Meta, a worker **claims** the recipient in PostgreSQL (one short
  transaction that creates the masked, pending message and sets the recipient's
  `message_id`, only while it is still `pending` with no claim). Only the worker that wins
  the claim calls Meta; duplicate jobs and a second worker leave it alone. The transaction
  is closed before the request is made, and the call has a deadline of its own (30 seconds).
- What a failed request proves is decided by the Meta **error code** together with a 4xx
  status, never by the status alone (Meta's reference does not map HTTP statuses to "not
  sent"):
  - **Refused** (`100`, `131008`, `131009`, `131021`, `131047`, `131051`, `132000`,
    `132001`, `132005`, `132007`, `132012`, `132015`, `132016`, `190`, `368`), a failure
    before the request was built, or a connection that was never established: provably not
    sent. The claim is released and `retry-failed` may try again (error prefix
    `meta_refused`); the sealed code is kept until its validity ends.
  - **Throttled** (`130429`, `131056`, `80007`): provably not sent and worth retrying
    later (`meta_transient`). Same handling.
  - **Anything else is unknown**: timeouts, connection resets, 408, 425, any 5xx, a bare
    429 or any other 4xx without a documented rejection code, an unreadable answer, or a
    worker that stopped after claiming. The recipient is marked failed with
    `delivery_uncertain`, **keeps its claim**, and the code is **never resent
    automatically**: `retry-failed` skips it (and reports `skipped_uncertain`). Meta may
    have delivered it.
- A claim that is never resolved (the worker died) is found **in PostgreSQL**, with no job
  having to come back from Redis: worker housekeeping runs every five minutes and declares
  it `delivery_uncertain` once it is older than a live send can be (twice the Meta call's
  timeout plus the time for the writes around it: 2 × (30 s + 30 s) by default). The
  update is atomic with that age check, so a live worker is never overridden; if one is cut
  off and its answer arrives late, the result is refused and the recipient stays blocked.
- A confirmed send is recorded on the message created by the claim (no duplicate messages),
  and delivery and read receipts update it as for any message.

#### Reconciling an uncertain delivery

`whatomate otp-uncertain` lists these recipients (phone shown as its last four digits),
including claims that are stuck and not yet resolved. To let one be sent again, **first
confirm with Meta's logs or the customer that the code was not delivered**, then:

```bash
whatomate otp-uncertain -release <recipient-id> -operator admin@example.com \
  -reason "no delivery in the Meta message log" -confirm-not-delivered -apply
```

- Without `-apply` it only checks and reports. `-confirm-not-delivered`, `-operator` and
  `-reason` are required.
- `-operator` must be a **real, active user of the campaign's organization** with the
  `campaigns:write` permission (or a super admin). The reason is audited and must not
  contain a code.
- It refuses when the code is no longer valid (or no longer stored).
- The release is a compare-and-set and an entry in the audit log (operator, recipient,
  campaign, date, reason) written in the **same transaction**: no audit, no release.
- It queues nothing. Only an explicit `retry-failed` sends it again.

### Deploying and operating (authentication campaigns)

- **Server and worker must run the same version, the same `app.encryption_key` and the
  same `[otp]` settings.** The server stores the codes sealed and queues them sealed; a
  worker from an older version would read the sealed value as a template parameter and
  fail every recipient (nothing is sent, but nothing is delivered either). The embedded
  workers (`server -workers N`) always match the server; separately started `worker`
  processes must be upgraded together with it.
- Drain or pause authentication campaigns before upgrading or rolling back.
- Start and retry are atomic: concurrent requests for the same campaign enqueue each
  recipient once and the extra requests get `409`.

The CSV import in the UI accepts a `valid_until` column for these templates, and the
import dialog has an optional "valid until" field for recipients without their own.

## Campaign Actions

### Start Campaign

Begin sending messages.

```bash
POST /api/campaigns/{id}/start
```

### Pause Campaign

Pause a running campaign.

```bash
POST /api/campaigns/{id}/pause
```

### Cancel Campaign

Cancel a campaign (cannot be resumed).

```bash
POST /api/campaigns/{id}/cancel
```

## Campaign Status

| Status | Description |
|--------|-------------|
| `draft` | Campaign created, not yet started |
| `scheduled` | Campaign scheduled for future sending |
| `sending` | Campaign is actively sending messages |
| `paused` | Campaign is paused |
| `completed` | All messages have been processed |
| `cancelled` | Campaign was cancelled |

## Rate Limiting

Campaigns automatically respect WhatsApp's rate limits:

| Tier | Messages per second |
|------|---------------------|
| TIER_1K | ~10 msg/sec |
| TIER_10K | ~30 msg/sec |
| TIER_100K | ~80 msg/sec |
| TIER_UNLIMITED | No limit |

<Aside type="tip">
  Start with smaller campaigns to warm up your account and improve your messaging tier.
</Aside>
