# Protocol send: idempotency and state contract

Endpoints (all need `occurrences:write`, `chat:write` and a valid tie to the case/channel; another organization or case is a 404):

- `POST /api/occurrences/{id}/send-protocol`: header `Idempotency-Key: <uuid>` is **required** (400 `idempotency_key_required` / `idempotency_key_invalid`). Body `{ "message"?: string }`.
- `GET /api/occurrences/{id}/protocol-sends/{send_id}`: state of one send.
- `GET /api/occurrences/{id}/protocol-sends?idempotency_key=<uuid>`: the same, for a caller that never saw the answer and does not know the `send_id`. It never claims the key and never sends. It is not strictly a pure read: asking about a stale `processing` claim (see Fencing) reconciles it (moves the state forward, never sends). 404 = the server holds no claim for the key (the request never arrived or is still in flight): it is **not** proof that nothing was sent until a request in flight has ended (the server gives up on the provider after 30 s).

- `GET /api/occurrences/{id}/protocol-sends?open=true`: the case's **open send** (state `processing`, or `uncertain` until a person settles it), whoever started it and from whichever device. 404 `send_not_found` = none. Same authorization as sending; `own` says whether the caller started it, never who did.
- `POST /api/occurrences/{id}/protocol-sends/{send_id}/resolve`: a person settles an `uncertain` send (below). It needs the permission `occurrences:resolve_send`, **not** `occurrences:write` or `chat:write`, plus the scope to see the case.

## Answers

| result | HTTP | `sent` | `confirmed` | meaning |
|---|---|---|---|---|
| `sent` | 200 | true | true | the provider accepted the message |
| `failed` | 502 (422 closed window, 400/500 other proven refusals) | false | true | proven NOT sent |
| `uncertain` | 202 | false | false | the provider may have received it; do not send again, check the conversation |
| `processing` | 202 | false | false | the same key is still being worked on; nothing new was sent |

**`confirmed` means the outcome of the operation is known. It never means the customer received or read the message** (delivery is reported separately by the provider's status webhooks).

Every answer carries `send_id` and `message_id`. A repeat of the same request answers with the stored result and the header `Idempotent-Replay: true`; the same key with a different text, destination, case or person is a 409 `idempotency_key_reused`. A new intention to send uses a **new** key.

## Retention and expiry

- `sent` and `failed` records are kept 90 days after they were **settled** (the provider's answer, the reconciliation or a person's decision). `processing` and `uncertain` records are **never** removed: an `uncertain` record is what keeps the case protected until somebody settles it.
- **After the record is removed the key is unknown**: repeating the same key later is read as a new intention and **sends again**. Keys are single-use by contract; the interface never reuses the key of a finished intention, and the browser drops its own record long before 90 days (24 h).
- A claim stuck in `processing` is judged by the fencing rules (below): never dispatched and older than 2 minutes -> fenced to `failed` (proven not sent); dispatched and past its owner deadline plus the margin -> reconciled from the audit trail and the message row, and with insufficient evidence `uncertain`. The key is never released and nothing is resent. A missing local record is never read as proof that the provider did not receive the request.

## How a send is classified (`failed` vs `uncertain`)

The state follows **where the send stopped and what the provider proved**, never the HTTP status alone. `failed` is only for a send that is proven NOT delivered; anything else that touched the provider is `uncertain`, the key stays taken and nothing is ever resent automatically.

| where it stopped | evidence | result |
|---|---|---|
| validation (window closed, no account, bad body) | nothing reached the provider | `failed` |
| the attempt record (audit) cannot be written | nothing reached the provider | `failed` ("nothing was sent") |
| the message row cannot be created | nothing reached the provider | `failed` |
| connection never established | no byte was written (`dial` error) | `failed` |
| provider answers 4xx with a documented refusal code (100, 190, 131047, ...) | the provider refused it | `failed` |
| provider answers with a documented throttle code (130429, 131056, 80007) | refused, retry later | `failed` |
| 4xx with a code Meta does not document as a refusal, 4xx without a Meta body, 408/425 | proves nothing | `uncertain` |
| 5xx, proxy page, reset, timeout after the call started | the provider may have accepted it | `uncertain` |
| provider accepted, but the audit **result** row cannot be written | the answer follows the provider, not the audit | `sent` / `uncertain` / `failed` as the provider said |
| provider accepted, but the intent row cannot be closed | stays `processing`; reconciled from the message row (provider accepted -> `sent`) or, with no evidence, `uncertain` | never `failed` |
| the process dies before the point of no return (never dispatched) | stale `processing` for 2 minutes, then fenced | `failed` (proven: the owner can never send) |
| the process dies after the point of no return | stale `processing` past the owner deadline + margin, reconciled by evidence | `sent` or `uncertain`, never `failed` |

A `failed` row of the local message (the HTTP client gave up) is **not** evidence that the provider did not receive the request.

## One open send per case

A case has at most **one open protocol send**: a send in `processing`, or `uncertain` until it is settled. **Scope of the guarantee**: in the current code `models.SendIntentKindProtocol` (`kind = 'protocol'`) is the only kind defined, and `claimSendIntent` is the only place that creates an `OccurrenceSendIntent` (outside tests); it writes that value. The index has `kind` in its key, so its guarantee is tied to that kind: a future kind of send would NOT be covered by this index unless someone decides that it shares the same lock (by changing the index) or gives it its own control. The column has no `CHECK` limiting `kind` to `protocol`, and this contract does not claim that the database or the claim rejects other values. The lock also does not cover the other customer sends (`SendMessage`, media, reactions, templates, `ReplyToOccurrence`), which do not use this table. While one exists, **nobody** can start another from that case: not another person, not another device or tab, not the same person with a new key or an edited text. Other cases (even of the same customer) and other organizations are not affected. `sent` and `failed` sends hold nothing.

- **The database enforces it**, not a check before the send: the partial unique index `uq_send_intent_open` on `(organization_id, occurrence_id, kind) WHERE state IN ('processing','uncertain')`. The claim is one `INSERT … ON CONFLICT DO NOTHING` (no conflict target), so the key index and this index are both enforced atomically, whatever the number of requests, users or servers.
- **Order of the answers.** The same key is answered first, from its own record (replay, `409 idempotency_key_reused`, `202 processing`). Only a different key that finds the case taken gets `409 send_pending`. A stale `processing` claim that is in the way is reconciled from the evidence first (it may have ended).
- **`409 send_pending`**: `error_type: "send_pending"`, `data: { result: "pending", sent: false, confirmed: false, send_id, state, own, claimed_at }`. It tells the page what to ask about and whether the caller started it. It never carries who started it, the text, or anything of another organization. Nothing is sent and no record is left for the refused request. It is a different answer from `idempotency_key_reused` and from the `202 processing` of the same key.
- **`uncertain` is never released by time.** Not by the reconciler, not by the retention, not after 72 hours or ten years. It leaves only by (a) the provider's own confirmation (a message id and an advanced status), which makes it `sent`, or (b) a person's decision.

### Settling an uncertain send (`resolve`)

A person who checked the conversation with the customer says what they found. It sends **nothing** and never resends.

- Body: `{ "outcome": "delivered" | "not_delivered", "conversation_checked": true, "note": "<what the conversation showed, 10 to 1000 characters>" }`. Anything else is 400 `resolution_invalid`.
- Authorization: `occurrences:resolve_send` **and** the scope to see the case (a supervisor settles only what is under their management; another organization is 404). The backend checks both; hiding the button is not the control.
- Only an `uncertain` send can be settled, and an `uncertain` send is one whose owner has finished or can no longer start a send (see Fencing); a send still `processing` is never settled by a person. Anything else, including a send somebody settled first, is 409 `send_not_uncertain`. The provider's own evidence wins: if the records show the provider accepted it, the send is settled as `sent` first and the decision is refused.
- Effect: `delivered` → state `sent`; `not_delivered` → state `failed`; the case is free for a new send. The intent records who, when, the outcome and the note; the decision, the new state and the audit entry are **one transaction** (if the audit entry cannot be written nothing changes).
- Permanent audit entry (`result: resolved_delivered | resolved_not_delivered`, with outcome, note, `conversation_checked`, previous state, send and message ids). It is final through the interface; a later correction is a new audited action, not an edit.
- `not_delivered` frees the case: if the message was in fact delivered the customer receives the next one as a duplicate. The interface says so before it is chosen.
- The state query then reports `resolved_by_person: true`, the outcome and the time, never who.
- Default grants: system roles `admin` and `manager`, and the presets `Supervisor de Loja` and `Supervisor de SAC`. SAC, Vendas, Logística, Jurídico and agent roles do not have it. Existing organizations receive it through an additive backfill with this exact behavior: it never revokes anything; an organization is skipped when its `admin` or `manager` system role already holds the permission (a new organization, or one already served), so a second run changes nothing; otherwise it grants those two roles and the two supervisor presets (also when the seed recreated a preset in the same boot); a role made by hand is never touched and never blocks it; two boots at once cannot fail on a duplicate link. What an administrator does afterwards: removing it from a supervisor preset or a custom role is never undone; removing it from BOTH `admin` and `manager` is undone at the next `-migrate`, because the data cannot tell "never granted" from "removed on purpose" (there is no stored marker). The backfill is not optional: if it fails, or the permission is not seeded, the boot STOPS with that error (it never skips silently), so the migration can never reach the index step with nobody allowed to settle sends. The permission name is `occurrences:resolve_send` (the action column of `permissions` is `varchar(20)`).

### Fencing: why a person can never free a send whose owner can still START a provider call

A send has an **owner** (the request that claimed it). The owner may call the provider only after it moved its row, in one atomic compare-and-set in the database, from "never dispatched" to "dispatched" (`dispatched_at`, with `dispatch_deadline = the database's NOW() + 40 s`). The compare-and-set is mandatory: the only code path that sends a protocol runs it as its `BeforeSend` point of no return, and a send with such a point cannot be asynchronous (`SendOutgoingMessage` refuses `Async=true` with `ErrBeforeSendNeedsSync`, because the async branch would drop the deadline). The provider request then carries three limits:
- a context deadline equal to the database's `dispatch_deadline`. Go turns that instant into a duration once, when the context is created, and arms a timer on the process's **monotonic** clock: a suspension (a process stop, a VM pause) that happens AFTER the context exists does not make it expire. What does look at the wall clock afterwards is the dialer's own deadline when a NEW connection is dialed, and the preflight below;
- the process's own monotonic timer, started before the compare-and-set was sent (the database's `NOW()` is taken after that instant, so this timer can never expire later than the database's deadline);
- a **preflight** that runs immediately before the request is handed to the HTTP client (`whatsapp.WithPreflight`): it asks the database, with the database's clock, whether the row is still `processing`, dispatched and inside its deadline, and checks the monotonic timer. A refusal means the request is not made, which is provably not sent: the send ends `failed` with the message "The send was cancelled before it was handed to the provider; nothing was sent" (the provider neither accepted nor refused anything).

So anyone who finds the row stale can tell, from the database alone, whether the owner can still start the call:

| row | what it proves | what happens |
|---|---|---|
| `processing`, never dispatched, claimed more than 2 minutes ago | the owner can **never** send: when it wakes up its own dispatch finds the row moved and sends nothing | the row is **fenced to `failed`** (proven not sent) by one compare-and-set (`... AND dispatched_at IS NULL`) that races the owner's dispatch; exactly one of the two wins, also against a reconciler holding a stale copy of the row |
| `processing`, dispatched, before `dispatch_deadline` + 30 s | the owner may still be calling the provider | nothing: still `processing`, the case stays closed, a person cannot settle it (it is not `uncertain`) |
| `processing`, dispatched, after `dispatch_deadline` + 30 s | the owner's own limits (deadline, monotonic timer, preflight) all refuse a call that has not started | settled from the evidence: the provider's confirmation -> `sent`, else `uncertain` (and only then can a person settle it) |
| `uncertain` written by the owner itself | the owner has finished: the answer it got (or lack of it) is final for that request | a person can settle it **at once**, with no margin (the 30 s only guard a send that is still `processing`) |

**Clocks.** Everything that decides whether a dispatched owner may still start a call (the deadline and the 30 s after it) is judged on the **database's clock**: the reconciler, the claim, the state query and the resolve read it with `SELECT NOW()`, and the owner's own limits are the database's deadline plus a monotonic timer that starts before its compare-and-set. **There is no fallback to the local clock.** When the database clock cannot be read: the background pass is skipped (and logged), the claim, the state query and a repeat of a key do not reconcile the row (it is reported as it is, still open, and a new send stays refused as `send_pending`), and the resolve answers 503 and changes nothing. A decision that frees or settles a send is never taken on a clock the deadline was not measured on.

The uses of the application server's own wall clock that remain are these, and none of them decides whether a dispatched owner may still call the provider: `claimed_at` (and so the 2-minute wait before a never-dispatched claim is fenced), and the timestamps it records (`finished_at`, `resolved_at`, the audit entries), which are used for display and for the 72-hour and 90-day windows. If the database runs more than 2 minutes ahead of an application server, a live owner that has not yet dispatched can be fenced earlier than intended: that is safe (the send ends `failed`, nothing is sent) but visible to the user, and it means the servers' clocks should be kept in sync (NTP).

**What this does NOT guarantee, stated plainly.**
- The provider offers no idempotency key and no fencing token, so a request the owner had **already handed to the network** before its deadline cannot be recalled: the provider may still process it later, and bytes already in the operating system's send buffer can be delivered after a long stall or a retransmission. The 30 s margin is an **operational allowance** (provider queueing, a request in flight at the deadline); it is **not** a guarantee that such a request was cancelled, and it does not bound it. That is why a send that ends without an answer stays `uncertain`, and why a person is asked to check the conversation before saying "not delivered".
- The preflight narrows the gap between the last verification and the write on the network, it does not close it. Between the preflight and the first byte the request can still wait for a pooled connection, DNS, a new connection (30 s dialer), TLS (10 s), a proxy CONNECT or an HTTP/2 stream slot, so on a cold connection the write can begin any time up to the deadline; the context cancels each of those steps. The Go transport can also re-send a request after the preflight without calling it again: over HTTP/1.1 only when nothing was written, over HTTP/2 when the server refused the stream (`REFUSED_STREAM`), sent a `GOAWAY` for a stream it did not process, or reset the stream with `RST_STREAM(PROTOCOL_ERROR)`, and that last case does NOT prove the server did not process the request. The HTTP/2 round tripper makes up to eight attempts per run of its retry loop (the first one and up to seven repetitions, the later ones after a backoff of about 1, 2, 4... seconds), replays the body from its buffered copy and does NOT run the preflight again. That count is per run of the loop, not per request: the application uses `http.DefaultTransport`, and after a `GOAWAY` its outer loop can open a NEW connection and run the HTTP/2 loop again with the counter reset. What bounds the whole request is the context deadline, not the number eight. No duplicate from those retries has been demonstrated, and none is claimed impossible: a send whose request may have been retried ends `uncertain`, never assumed safe. A process frozen after the preflight returns and before the operating system performs the write (a process stop, a VM pause, starvation) can still write later: the context deadline is enforced by a runtime timer, and the HTTP/1.1 transport writes the request in another goroutine with no further check. That residue is irreducible with the provider's API and it is the reason the state is `uncertain`, not `failed`.
- A process that is suspended after its provider context was created finds that context (and the monotonic timer) NOT expired when it resumes: neither counts the suspension. What covers a suspension that ends BEFORE the preflight is the preflight itself, which asks the database with the database's clock. A suspension that begins after the preflight returned is not covered by anything: that is the residue above.
- What is guaranteed, and tested, is narrower: **no NEW provider call is started by an owner that was fenced, or whose dispatch deadline has passed, or whose row is no longer `processing` in the database at the preflight**, and an owner that never dispatched can never send at all.

Tests (real database): the owner is stopped before and after its point of no return while the reconciliation, a person and a new send act, then released; the dispatch-versus-fence race runs for real and the test asserts that BOTH the dispatch and the fence are seen winning (at least 120 rounds, and more until each has won at least five times, with a cap), with the property checked in every round; the fence acting on a stale copy cannot catch an owner that has since dispatched; nothing is anticipated between the deadline and the deadline plus the margin; the preflight stops the request when the database says the deadline is past even though the owner's own timers have not expired.

Rolling deploys: rows claimed by a binary that does not know the dispatch step have `dispatched_at` empty; deploy backend and frontend together (already required) so that no such send is in flight during the switch.

### Reconciliation

Two separate queries, so an old `uncertain` can never keep a newer stale `processing` waiting: (1) stale `processing` claims (never dispatched and older than 2 minutes, or dispatched and past the owner's deadline plus the margin: see Fencing), oldest first, in batches of 200; (2) unsettled `uncertain` ones **finished within the last 72 hours**, newest first, batch of 200. The 72 hours only bound how long the background loop keeps re-reading an uncertain send (provider confirmations arrive within hours); they never bound the protection: after them the send stays open, the case stays blocked, the record is kept, the state query still upgrades it if a confirmation arrives later, and a person can still settle it. Reconciliation never sends, never frees a key and never turns `uncertain` into `failed`.

## Deployment: migration, order and rollback

**Required migration.** The table `occurrence_send_intents` is created by GORM AutoMigrate (`internal/database/postgres.go`), and AutoMigrate only runs when the backend starts with the `-migrate` flag (`whatomate server -migrate`). **Without it the table does not exist and the protocol send does not work** (every `send-protocol` fails; the recovery endpoints fail too). The migration is additive: it creates a new table and its indexes, adds the columns `dispatched_at` and `dispatch_deadline` to it, and adds one permission row; no existing table schema is changed (the permission name fits the existing `permissions.action varchar(20)`) and no existing row is modified, except that `-migrate` also grants `occurrences:resolve_send` to the roles listed above (additive; see the exact behavior under "Settling an uncertain send").

The one-open-send index `uq_send_intent_open` is created by the migration code (`EnsureOpenSendIntentUniqueness`), not by AutoMigrate, as the **last step of the whole `-migrate` boot**: after the schema, the permission seed, the roles and every backfill. **If the table already holds a case with more than one open send, that last step STOPS the boot with an error that lists each case (organization, case, the send ids, dates); everything else is already done, nothing is created for the index, and no row is ever deleted or edited.** Recovery, with no SQL: start the server **without** `-migrate` (customer sends from cases stay refused while the protection is missing; everything else works), have a person who holds `occurrences:resolve_send` settle each listed send after checking the conversation (`POST …/protocol-sends/{send}/resolve`; a send still `processing` is settled by the reconciliation within minutes), then run `-migrate` again. A new installation, and any production database that has never run this feature, cannot have such rows. The read-only diagnostic is `database.OpenSendIntentDuplicatesSQL`.

**An existing index with the right name but the wrong shape fails the migration.** `CREATE UNIQUE INDEX IF NOT EXISTS` only looks at the name, so the migration verifies what it finds or creates (`VerifyOpenSendIntentGuard`) and, if it is not the protection (not unique, not valid, other columns, a predicate that misses an open state), stops with an error that does not touch the index and says what to do: from `psql`, as the owner of the table, `SET lock_timeout = '5s'; DROP INDEX uq_send_intent_open;` (an index only, no data is involved) and run the migration again, which creates it correctly. `DROP INDEX` waits for an exclusive lock on `occurrence_send_intents`, and while it waits every other access to that table queues behind it, which is what the `lock_timeout` is for (if it times out, try again when no long transaction is open; the server default is no timeout). `DROP INDEX CONCURRENTLY` does not hold the table for long, but it cannot run inside a transaction block and, if cancelled, leaves an INVALID index that must be dropped as well. The role that runs it must own the table. Until the migration has run, customer sends from cases answer 503 and nothing else is affected; no duplicate can be inserted in between, because the guard runs after the INSERT of every claim. If the wrong index had allowed duplicates, the first migration reports the duplicates (see above) and the next one the index: two passes. A leftover of a cancelled `DROP INDEX CONCURRENTLY` or of a failed `CREATE INDEX CONCURRENTLY` is the usual cause. Customer sends stay refused until then.

**A name held by something that is not an index.** If the reserved name `uq_send_intent_open` is held in the current schema by a sequence, a table, a view or another non-index relation, `CREATE UNIQUE INDEX IF NOT EXISTS` skips silently; the migration reports the name as held by that kind of object (`OpenSendIntentNameTakenError`), says that `DROP INDEX` does not apply to it, and does not touch it. The operator finds out what it is and removes or renames it with the statement for its own kind, then migrates again. If the name is held by a plain INDEX of another table the message says so and `DROP INDEX` is the right statement. If that index belongs to a UNIQUE, PRIMARY KEY or EXCLUDE constraint (of that table or of `occurrence_send_intents` itself, as a non-partial UNIQUE constraint with the right name), Postgres refuses `DROP INDEX` with 2BP01 because the constraint needs the index: the message then names the constraint and its table and says `ALTER TABLE <table> DROP CONSTRAINT <name>` instead (with the same `lock_timeout` caution). Nothing is deleted in either case, and sends stay refused (503) until then.

**The server refuses to send while the protection is missing (fail closed), checked inside every new claim.** The claim is one transaction: the `INSERT` of the intent and then a check that `uq_send_intent_open` exists, is UNIQUE, is VALID, is a btree, UNIQUE, VALID, READY and live, on exactly the three plain columns `(organization_id, occurrence_id, kind)` in that order (no expression, no extra key column, no INCLUDE column), with the partial predicate "state is processing or uncertain" and nothing else. Postgres stores `state IN ('processing','uncertain')` as `state = ANY (ARRAY['processing','uncertain'])` and renders it with casts and parentheses that differ between versions, so the check removes the casts to a character type and the whitespace and requires what is left to be exactly one of TWO shapes, each anchored at both ends: `state = ANY (ARRAY[L1, L2])` (the index as the migration creates it) or `state = ANY (ARRAY[(L1), (L2)])` (the same index as `pg_dump`/`pg_restore` leaves it, with each element parenthesized and cast; checked on PostgreSQL 16.15 and 17.11, where the previous single-shape check refused a restored database and left sends disabled). Both allow balanced parentheses around the parts, with `L1` and `L2` the two literals `'processing'` and `'uncertain'`, distinct, in either order. The two shapes are not mixed, and a parenthesis only wraps a whole literal, exactly once (an array of one ROW such as `ARRAY[('processing','uncertain')]`, or a doubly parenthesized element, does not match). **The string literals are checked before anything is normalized, exactly as written:** there must be exactly two, one `'processing'` and one `'uncertain'`; a literal with a space, a line break, a cast spelled inside it (`'pro::textcessing'`), an escaped quote or an `E'…'` prefix is refused, because the normalization below would otherwise turn it into `'processing'` while the index does not cover `processing` (found by the independent review of `855ad22d`; reproduced on PostgreSQL 17.11). The casts and whitespace are only taken out after that check, so nothing inside the quotes is changed by it. Outside the literals, nothing is stripped from the middle, so a constant comparison, a comparison of two booleans or two arrays, a column inside the array, `ALL` for `ANY`, a one- or three-element array, `NOT`, `<>`, OR/AND, another column, a function or a time condition does not match. It is looked up on the table `occurrence_send_intents` of the **current schema** only: a table or an index of the same name in another schema counts for nothing. The check follows the `INSERT` on purpose: once the `INSERT` has run, the transaction holds a lock on the table that `DROP INDEX` must wait for, so an index that is there when it is checked stays there until the claim commits. If the protection is missing or wrong the transaction is rolled back and the endpoint answers `503 send_guard_unavailable` ("Customer sends from cases are unavailable… Nothing was sent. An administrator must run the migration (-migrate); if it reports an invalid or wrong index, follow what it says."): nothing is claimed and nothing is sent, whatever the key. **There is no cache and no trust window**: an index dropped right after a good send is seen by the very next one, and a server whose migration was just run sends again without a restart. A repeat of a key that already exists inserts nothing and still replays its stored answer. The boot logs an error when the protection is missing. Reading and settling sends are not affected.

**Order.**
1. Back up the database.
2. Start the new backend **once with `-migrate`** (with the new binary), before the new version is made available to users, and wait for the boot to finish.
3. Verify the table and the indexes (below). Only then release the flow.
4. Deploy the new frontend **together with** the new backend. The backend now requires `Idempotency-Key` on `send-protocol` (400 `idempotency_key_required`), so an old frontend cannot send protocols against the new backend, and the new frontend depends on the recovery endpoints of the new backend. Do not leave one side on the old version.

**Verification before releasing the flow** (read-only):

```sql
-- the table exists
SELECT to_regclass('public.occurrence_send_intents');            -- must not be NULL
-- the UNIQUE index that makes "one key, one send" true in the database
SELECT indexdef FROM pg_indexes
 WHERE tablename = 'occurrence_send_intents' AND indexname = 'uq_send_intent_key';
-- expected: CREATE UNIQUE INDEX uq_send_intent_key ... (organization_id, idempotency_key)
-- the index that makes "one open send per case" true in the database
SELECT indexdef FROM pg_indexes
 WHERE tablename = 'occurrence_send_intents' AND indexname = 'uq_send_intent_open';
-- expected: CREATE UNIQUE INDEX uq_send_intent_open ... (organization_id, occurrence_id, kind) WHERE state IN ('processing','uncertain')
-- (the server checks this itself: it refuses customer sends from cases when it is missing or invalid)
-- the permission exists and the intended roles hold it
SELECT r.name, r.organization_id FROM custom_roles r
  JOIN role_permissions rp ON rp.custom_role_id = r.id
  JOIN permissions p ON p.id = rp.permission_id
 WHERE p.resource = 'occurrences' AND p.action = 'resolve_send' AND r.deleted_at IS NULL;
-- the other indexes: idx_send_intent_occurrence, idx_send_intent_pending (partial, state = 'processing'),
-- idx_send_intent_uncertain_recheck (partial, state = 'uncertain' AND reconciled_at IS NULL)
SELECT indexname FROM pg_indexes WHERE tablename = 'occurrence_send_intents' ORDER BY 1;
```

If `uq_send_intent_key` or `uq_send_intent_open` is missing, do **not** release the flow: without the first two requests with the same key can both send, and without the second two people can send to the same customer from one case at the same time.

**Rollback.** Going back to the previous binary (and frontend) does not require removing the table: the old code ignores it. **Do not drop the table or delete rows as part of a rollback**: the rows are the record of which keys were already used (and, for `uncertain`, of sends that may have reached the customer); removing them frees the keys and a repeated request would send again. Drop it only by a separate, explicit decision once no new-version client can still repeat a key. Rolling back backend and frontend together is the same coordination as deploying them. A previous binary that does not know `uq_send_intent_open` is stopped by it, not harmed: a send that finds the case taken fails with "nothing was sent" instead of overlapping. Drop that index only as part of the same separate, explicit decision.

## What the browser treats as an answer (frontend rules)

- Only the application's own answer **closes** an intention (the browser forgets the key): a body that carries the `send_id` (sent, failed or uncertain are answers about that send), or an application error envelope (`status: "error"`) with a 4xx status (key missing or invalid, not allowed, not found, key reused, closed window).
- A 4xx envelope closes the intention only on the **first** request under a key. On a **retry** it proves only that the retry was refused (409 after the contact data changed, 429, 401/403 after the session or access changed), not what became of the earlier request; the key stays and the page asks the server. Only a body with the `send_id`, or the server answering `sent`/`failed` to the state query, closes it.
- Every request under a key restarts the 60 s in-flight grace (`savedAt` is renewed), because the newest request may still be on its way.
- `409 send_pending` on a new intention means **another send of the case is open**: the key of the refused request was never used, so nothing stays pending for it. The page does not show an error: it asks `?open=true`, shows the pending state (and says another message is open when `own` is false) and offers to settle it only to someone holding `occurrences:resolve_send`.
- `503 send_guard_unavailable` means the server refused to start the send because its own protection is missing: nothing was claimed or sent, no key was used, so the intention is closed (any other 503, such as a proxy's, keeps the key).
- A 404 means "no claim for that send or key" **only** when it is the application's own `send_not_found`. Any other 404 (case or contact gone, a route a proxy or older backend does not know) concludes nothing: the record stays.
- The copy of the record kept in the page's memory obeys the same 24 h as the browser storage.
- Anything else is **no answer**: a timeout, a lost connection, and also a 5xx (or an envelope-less 4xx such as 413/429) from a proxy or load balancer, for example 502/503/504 while the backend restarts. The key is kept and the page asks the server (by `send_id` or by key); it does not send again.
- While an intention is unresolved, the form does not accept a **different text** for the same case: it does not mint a second key (that would be a second message while the first may be in flight or delivered). The text is locked and the page shows the pending state until the server says `sent` or `failed`.

## Known limits and operational notes

- **Only the renderings seen on PostgreSQL 16.15 and 17.11 are accepted.** The predicate check is written not to depend on the exact text (casts and parentheses are normalized) and accepts the two shapes described above: the migration's own index and the same index after `pg_dump`/`pg_restore`. Both renderings were observed on a real PostgreSQL 16.15 and 17.11, and the tests run on both; other versions are not verified. A different rendering would make the check refuse the correct index (fail closed: sends refused until it is looked at), never accept a wrong one. Partitioned tables and a real pgbouncer were not checked. **ENUM and domain columns**: no automated test covers them. They were checked by hand, once, with psql on a disposable PostgreSQL 17.11 during the independent review of `12b2fa68`, and only the rendering was looked at: a column of ENUM type renders the predicate with the enum type (`'processing'::st_enum`), which the cast-stripping does not remove, so by reading the code the check refuses it (fail closed); a domain over `varchar` renders exactly like the real column, so by reading the code it is accepted, which is the right behavior because it means the same. The accept/refuse decision itself was deduced from the code, not run through the Go check. The model uses `varchar(16)`.
- **What the handler test of a taken name does and does not show.** `TestSendGuard_TheNameHeldByAnotherObject_IsRefusedFailClosed` replaces the guard's verifier with one that reads a separate scratch database, so the 503 in that test comes from the replacement: it shows that any guard error gives `503 send_guard_unavailable`, rolls the claim back, that the error the real verifier reports for that database is the "name taken" error, and that sends work again after the repair. It does not show that the real verifier, running inside the claim transaction, sees the object that holds the name. That part is covered by `TestSendGuard_TheCheckRunsInsideTheClaimTransaction_AndARefusalRollsItBack` and by the database tests of `EnsureOpenSendIntentUniqueness` / `VerifyOpenSendIntentGuard`. A reserved name held by an index of ANOTHER table exists only in the database tests, not in the handler test.
- **A session-local temporary table can shadow the real one.** A session that creates `TEMP TABLE occurrence_send_intents` writes to `pg_temp` while `current_schema()` stays the same, so the check looks at the real table and passes while that session's rows go elsewhere. The application never creates temporary tables; this is outside the threat model and is recorded here so nobody reads the check as a defence against it.
- **Updates that move a row back to an open state** are enforced by the index but do not run the in-claim check (only new claims do).
- **Running the tests that touch the database.** Two settings avoid waiting without a limit, and neither is a default: (1) give `go test` an explicit `-timeout` BELOW the point at which the outer tooling kills the run (for example `-timeout 15m`): the test binary's own timeout dumps the stack of every goroutine, which names the blocked query, while the outer "ran too long" kill dumps nothing; (2) put `options=-c lock_timeout=60000 -c statement_timeout=300000 -c idle_in_transaction_session_timeout=120000` (URL-encoded) in `TEST_DATABASE_URL`: the server defaults are all 0, so a `TRUNCATE ... CASCADE` in the test helpers can wait indefinitely behind any session that holds a lock (reproduced), and a test that leaves a transaction open would make a later test wait. The options carry over to the scratch and migration databases because they keep the URL's query string. For a long run also: keep the machine awake, run with `-json` (or `-v` piped through a timestamping tee) to get a time per test, and on a stall look at `pg_stat_activity` and `pg_locks` (`wait_event`) before killing it.
- **The 33-minute stall of the `internal/database` test package is NOT resolved, and no cause is established.** On 2026-11-05 one run of that package was killed after 33 minutes (`-timeout 30m`: the outer kill came at 30 minutes plus a 3-minute grace); the same package ran in 143 to 213 seconds in every other run, later ones included, and a later passing run neither explains nor resolves the stall. **One hypothesis**: the machine was in Modern Standby. What supports it: the Windows System log (Kernel-Power 506/507) shows the machine entering standby at 07:33:38, leaving and re-entering at 07:45:18 and leaving at 08:04:29, which covers most of the run, and the run's output file was last written at 08:05:37, a minute after the last resume. What does NOT support it, or is unknown: the absence of a goroutine dump from the test binary proves nothing either way (on Windows the Go runtime's monotonic clock reads the interrupt time, which Microsoft documents as including time spent asleep, so the binary's own timer may well have fired soon after the resume, or the outer kill may simply have come first; whether the interrupt time advances during Modern Standby on this machine was not confirmed); the start time of the stalled run is not known; nobody observed the suspension stopping the run; and there is no per-test timestamp. **Another possibility that was not excluded**: a wait behind a lock held by another session. Any statement in those tests can wait indefinitely while `lock_timeout` is 0, not only the `TRUNCATE ... CASCADE` helpers (reproduced in isolation) but also, for example, the six concurrent backfills of the backfill test, which are joined without a bound. Nothing observed in the stalled run singles either out. When it happens again, the settings above (explicit `go test -timeout` below the outer kill, whose own timeout dump gives the Go call site of every blocked goroutine, not the SQL text; the server-side timeouts; per-test timestamps; `pg_stat_activity` and `pg_locks` before killing) are what would tell them apart.
